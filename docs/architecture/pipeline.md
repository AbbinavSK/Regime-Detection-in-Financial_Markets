# Pipeline architecture

The pipeline runs in three disk-based stages, each stage's notebooks/scripts reading the previous stage's output from disk (not in-memory handoff), plus a 4th stage that runs downstream of stage 3's frozen model bundles. This doc covers *how the code is wired together*, not *what the methods compute* (see [`../math/`](../math/)) and not *what can currently be concluded from the results* (see [`../critical-evaluation.md`](../critical-evaluation.md)).

## Stage 1: Data acquisition

**`data_download_sp500.ipynb`** / **`data_download_nikkei225.ipynb`** / **`data_download_ftse350.ipynb`** / **`data_download_csi300.ipynb`** — four self-contained notebooks (no backing library module), one per market group, each carrying its own copy of the same `INDICES`-registry pattern and the same `fetch_constituents`/`download_prices`/`screen_panel`/`download_index` functions verbatim rather than importing them from a shared module. All four share `START_DATE = "2001-01-01"`, `END_DATE = "2026-07-15"`, `BATCH_SIZE = 50`.

**`fetch_constituents(index_code)`** branches on which config shape that index's `INDICES` entry has:
- `wiki_url` + `table_index`/`sector_col` — S&P 500's Wikipedia table, positional.
- `wiki_url` + `table_match` — FTSE 100/250's Wikipedia tables, column-name-matched (their table order isn't stable, and the two pages' sector-column headers differ in casing). FTSE's `sector_map` (`FTSE_SECTOR_MAP`, a module-level constant shared by both the FTSE100 and FTSE250 `INDICES` entries) covers 99 raw ICB strings across both pages' casing variants, mapped to 11 short sector codes; its fallback (any unmapped sector prints a warning and falls back to `sector_name.replace(" ", "_").upper()`) never fires today against the live pages, but would silently invent a bucket rather than error if either page's wording changes.
- `wiki_url` + `table_match` + `suffix_col`/`suffix_map` — CSI 300's Wikipedia table, column-name-matched like FTSE, but additionally needing a per-row exchange-dependent `yfinance` suffix (`.SS`/`.SZ`) since its constituents trade across two exchanges rather than one, read from a dedicated `Exchange` column rather than parsed out of the ticker string itself.
- `components: {sector_code: [ticker, ...]}` — Nikkei 225, no equivalent scrapeable table, hardcodes a dated snapshot instead (`snapshot` field records the date; 225 tickers across 34 sector buckets), sector codes used directly as dict keys.

The three `wiki_url` shapes scrape live and each carry their own `sector_map` dict translating GICS/ICB/Segment sectors to short codes (CSI300 reuses several of S&P 500's own GICS-derived codes for matching categories rather than FTSE's distinct ICB-derived ones — a pre-existing cross-market inconsistency in the sector-code vocabulary).

**`download_index(index_code, ...)`** downloads adjusted-close prices via `yfinance`, tags each ticker with a `{SECTOR}_{TICKER}` column name, runs the panel through `screen_panel`, and writes `data/{index_code}_AdjClose_Raw.csv` / `data/{index_code}_AdjClose_Cleaned.csv`. Each notebook pins `END_DATE` to a fixed past date rather than `date.today()` — yfinance can leave the most recent trading day's row almost entirely `NaN` for most tickers (feed lag), which would otherwise cascade through `screen_panel`'s incomplete-history screen; pinning the date avoids the trap rather than fixing `screen_panel` itself.

**`screen_panel(df)`** runs five screens in a fixed order, each operating on the survivors of the one before it:
1. **Non-positive price** (`(df <= 0).any()`) — catches `yfinance` adjustment-factor artifacts (an impossible negative price), not real corporate events. Drops columns.
2. **Jump** (`|log-return| > 0.8`, an unnamed inline literal) — catches unadjusted corporate actions and other single-day adjustment glitches; also catches a handful of genuine historic crash days, an acknowledged, unresolved tension between "broken data" and "real extreme volatility" that a single magnitude cutoff can't separate. Drops columns.
3. **Incomplete history** (`dropna(how="any", axis=1)`) — drops any ticker with even one missing observation across the full backfilled span; mostly genuine late-IPO names (the mechanism behind this project's survivorship bias, see below), but also a small number of otherwise-pristine, full-span names dropped for a single isolated data-feed gap. Drops columns.
4. **Non-trading day** (row-wise: `>98%` of surviving names flat to `1e-12` on a given day) — catches exchange-wide holidays where `yfinance`'s fixed daily date range still returns a stale/carried-forward row (S&P 500 catches zero rows here, since its US-calendar download already excludes NYSE holidays; the other three markets catch their respective national holiday calendars). Drops rows.
5. **Prolonged trading halt** (column-wise: `HALT_STREAK_DAYS = 63` consecutive near-zero-return days for one stock, a local constant inside `screen_panel`, uniform across all four notebooks) — see below. Drops columns.

Steps 4 and 5 are deliberately ordered non-trading-day-first: measuring a stock's longest flat streak *after* exchange-wide holiday rows are already removed means the streak reflects genuine stagnant trading, not holiday-driven inflation.

**`HALT_STREAK_DAYS` is fixed at 63, uniformly across all four markets.** The real failure condition step 5 exists to prevent: a rolling correlation window (`networks.rolling_correlations`) is undefined — a stock with zero variance inside the window produces a `NaN` row/column in that window's Pearson correlation matrix, which then silently propagates through graph construction (`threshold_graph`'s `C[i,j] > threshold` is `False` for `NaN`, so the edge is just missing — no error, no warning). This happens whenever a stock's longest flat streak reaches or exceeds `epoch_length`, the number of trading days in a rolling window. Since `data_processing.py`'s `EPOCH_CONFIGS` builds three window lengths (378/132/63 days), the binding constraint is always the *shortest* one — a streak that's safe for a 132-day window can still corrupt every 63-day window it fully covers. `HALT_STREAK_DAYS = 63 = min(epoch_length)` is the largest threshold that still guarantees safety at every window length simultaneously, and therefore also the value that removes the fewest stocks subject to that hard constraint. This is a genuine Stage 1/Stage 2 coupling, not a free Stage 1 parameter: if `EPOCH_CONFIGS`' minimum `epoch_length` is ever lowered, `HALT_STREAK_DAYS` must be re-derived (lowered to match), or the same silent-`NaN` failure mode reopens.

**FTSE 350 is a post-hoc concatenation, not its own `INDICES` entry.** `data_download_ftse350.ipynb` runs `download_index` twice — once for `"FTSE250"`, once for `"FTSE100"` — each independently screened against its own sub-panel (a name is judged only against its own tier's panel, not the combined one), producing four files (`FTSE250_AdjClose_{Raw,Cleaned}.csv`, `FTSE100_AdjClose_{Raw,Cleaned}.csv`). It then concatenates the two *cleaned* panels (`pd.concat([df_ftse100, df_ftse250], axis=1, join="inner")`, FTSE 100 columns first) into `data/FTSE350_AdjClose_Cleaned.csv` — there is **no `FTSE350_AdjClose_Raw.csv`**, and the `join="inner"` means the combined panel's date range is whichever is shorter of the two tiers' cleaned date ranges.

**Known gotchas, flagged not fixed**:
- `BT.A` (BT Group's A shares) is the only dotted ticker across both FTSE tiers; the single-transform `epic.replace(".", "-")` (the same line S&P 500 uses for `BRK.B`) happens to resolve it correctly (`BT-A.L`) with no retry logic needed.
- No investment-vehicle screen is applied to any market (explicitly reverted after being built, to avoid survivorship bias) — full scraped universes go through ticker construction and price screens on equal footing.
- The 0.8 log-return jump threshold's justification does not fully transfer identically across all four markets' different price-limit conventions, but is kept as-is across all markets for consistency.
- Every notebook scrapes *today's* constituent list and backfills full history — any name delisted or dropped from an index at any point in the backfilled window never enters the corresponding panel (survivorship bias, common to all four notebooks).
- `download_prices`' `yfinance` calls occasionally fail transiently under `threads=True` — a failed ticker lands as an all-`NaN` column and is correctly absorbed by the incomplete-history screen either way, never silently missing from the raw panel entirely.

VIX is downloaded in `data_download_sp500.ipynb` (its last data cell) to `data/VIX_Close.csv` and is not index-parameterized (it's specifically the S&P 500's options-implied volatility index) — this is also why the other three markets have no VIX-equivalent validation anywhere downstream (see Stage 3). No other market has any validation series downloaded at all.

Each of the four notebooks ends with diagnostic plots (mean adjusted close, an all-constituents price overlay on a log y-axis, an all-constituents log-return overlay, and a plot of the raw prices of whichever stocks the halt screen removed — empty-case handled with a printed message if none were removed), using `plot_style.set_publication_style()`/`style_axis(ax, grid=True)`/`format_date_axis()`/`NEUTRAL_COLOURS["primary"]` — no regime shading, no `save_figure` (`plt.show()`-only, matching the walkthrough notebooks' display-only convention, since these are pre-modelling sanity checks with no regime labels or train/test split to show yet).

A future market would most likely get its own fifth `data_download_*.ipynb` following the same shape; verify its actual constituent-source structure before adding one rather than guessing.

## Stage 2: Data processing

**`data_processing.py`** — uses `networks.py` to turn prices into rolling-window correlation networks. Loops over all four markets (`INDICES = ["SP500", "Nikkei225", "FTSE350", "CSI300"]`), and within each index over the three `(epoch_length, epoch_shift)` configs (`(378,22)`, `(132,10)`, `(63,5)`) — `EPOCH_CONFIGS`' minimum `epoch_length` (63) is the value Stage 1's `HALT_STREAK_DAYS` is derived from (see Stage 1 above); the two are coupled, not independent constants — building and saving the raw correlation arm at each epoch length via `build_arm_networks(..., threshold=ARM_THRESHOLDS["raw"], index_code=index_code)` (`ARM_THRESHOLDS = {"raw": 0.65}`, derived in `threshold_diagnostics.ipynb` from S&P 500/T=132 data only — see [`../math/graph-filtering.md`](../math/graph-filtering.md) for the still-open external-validity gap this leaves), applied globally across markets. The pipeline previously also built `mg` (RMT bulk-clipped) and `gr` (market-mode-removed) arms; both were dropped since the regime-detection analysis only ever depended on `raw`. The `arm` dict field and `{arm}`-keyed filename remain, now always `"raw"`, for compatibility with `load_arm`'s existing call sites. Each arm dict carries its `index_code`, which `save_arm`/`load_arm` use to key the pickle filename: `outputs/{index_code}_raw_network_data_{epoch_length}d.pkl` — **12 files total** (4 indices × 3 epoch lengths). `load_arm` defaults `index_code="SP500"` so any call site that doesn't pass `index_code` explicitly resolves to the S&P 500 pickles.

## Stage 3: Modelling branches

Three parallel branches, sharing the same upstream pickles and, downstream of embedding, the same `modelling.py` machinery (`split_train_test`, `cluster_kmeans`/`cluster_hmm`, `fit_regime_order`/`apply_regime_order`, `validate_regime`, `empirical_transitions`):

- **`modelling_sweep_raw.py`** + **`modelling_walkthrough.ipynb`** (Graph2Vec) — each loads a pickled arm via `networks.load_arm`, splits it causally into train/test (`epoch_dates <= "2019-12-31"` vs. after) via `modelling.split_train_test`, fits Graph2Vec/StandardScaler/PCA/K-Means/HMM on train only (`modelling.fit_embed`, `cluster_kmeans`, `cluster_hmm`), and predicts/transforms both splits. The crisis regime is identified once from train (`fit_regime_order`) and frozen for everything downstream (`apply_regime_order`, `validate_regime`, `empirical_transitions`) — nothing re-derives it from test labels. VIX validation (`validate_regime`) only runs for `index_code="SP500"` (no other market has a realised-vol series wired up). `modelling_sweep_raw.py` runs the raw-arm Graph2Vec grid — `index_code x epoch_length x graph_type` = 4 × 3 × 3 = **36 combos**, all four markets, `graph_type` including the plain `threshold` graphs alongside `mst`/`tmfg` — writing `outputs/modelling_sweep_results_raw.csv`/`outputs/transition_matrices_raw.pkl` and one `outputs/models/{tag}.joblib` per combo.
- **`eigencentrality_sweep_raw.py`** + **`eigencentrality_walkthrough.ipynb`** (eigenvector centrality) — a parsimony benchmark against Graph2Vec: does a deterministic, hyperparameter-free descriptor (the leading eigenvector of each window's binary adjacency matrix, see [`../math/eigencentrality.md`](../math/eigencentrality.md)) detect regimes as well as Graph2Vec's learned representation? Reuses the *exact same* `split_train_test`/`cluster_kmeans`/`cluster_hmm`/`fit_regime_order`/`validate_regime` machinery from `modelling.py` — only the embedding step differs. Its grid is `index_code x epoch_length x graph_type`, but **`graph_type` is restricted to `["mst", "tmfg"]`** — the plain `threshold` graph is excluded because it isn't guaranteed connected (measured: 43% mean node coverage of the largest connected component across 629 SP500/132d windows), which breaks the fixed-dimension, consistently-indexed feature matrix this method needs. Runs the raw-arm grid across all four markets (4 × 3 × 2 = **24 combos**), writing `outputs/eigencentrality_sweep_results_raw.csv`, `outputs/transition_matrices_eigencentrality_raw.pkl`, and one `outputs/models/{tag}_eigencentrality.joblib` per combo.
- **`spectral_sweep_raw.py`** + **`spectral_walkthrough.ipynb`** (spectral/RMT) — the complementary control to the eigencentrality benchmark: instead of varying the descriptor while holding the input (the filtered graph) fixed, this varies the *input* while holding the descriptor style fixed. It skips graph filtering entirely — `spectral.window_spectral` eigendecomposes the arm-transformed `correlation_matrices` directly via `np.linalg.eigh`, with no `graph_type` axis at all (see [`../math/spectral.md`](../math/spectral.md) for the current 9-scalar feature list). Reuses the same shared machinery as the other two branches via `spectral.fit_spectral_embed`/`transform_spectral_embed`. `ARMS = ["raw"]` only, all four markets, giving `index_code x epoch_length` = 4 × 3 = **12 combos**. Also pickles one `outputs/{index_code}_spectral_features_{epoch_length}d.pkl` per combo — the per-window feature table itself, a first-class output in its own right — plus one `outputs/models/{tag}_spectral.joblib` and `outputs/transition_matrices_spectral_raw.pkl`.

All three sweep scripts share `K=3`, `TRAIN_TEST_CUTOFF = "2019-12-31"`, `n_seeds=20` default, and take `--quick`/`--n-seeds` CLI flags.

**The three `*_walkthrough.ipynb` notebooks were not widened alongside the sweep scripts' market scope.** Each is a fixed single-cell narrative (`ARM="raw"`, `EPOCH_LENGTH=132`, and for the two graph-based methods `GRAPH_TYPE="mst"`), run as two sequential sections — S&P 500 first, then Nikkei 225 (`INDEX_CODE` reassigned partway through the notebook, not looped) — sharing local `plot_regime_timeline`/`plot_vix_overlay` functions defined once and reused for the second section. FTSE 350 and CSI 300 do not appear in any walkthrough. The Nikkei 225 section has no F1/VIX-overlay cells (VIX validation is S&P-500-only). `modelling_walkthrough.ipynb` additionally contains, in its S&P 500 section only, the K-means elbow (`k=2..9`, train-only inertia) and HMM AIC scan (`n=2..9` states, best-of-10-seeds) that originally justified `k=3` pipeline-wide — this is the **only** place either diagnostic exists; no sweep script and no other walkthrough repeats it, and no silhouette or BIC scan exists anywhere in the codebase.

## Stage 4: Embedding geometry

**`embedding_geometry_sweep.py`** + **`embedding_geometry.py`** (no walkthrough notebook) — downstream of `modelling_sweep_raw.py`'s frozen bundles only, not a regime-detection branch (fits no clustering of its own): is Graph2Vec's embedding *shape* stable across the three nested network constructions (threshold, MST-threshold, TMFG-threshold)? Graph2Vec only — eigencentrality and spectral are not used by this branch. Unlike stages 1-3, it is **not** a full-grid sweep: `INDEX_CODE = "SP500"` is a fixed module constant with no CLI override (no other market); the distance metric is fixed to cosine and MDS is fixed to 2 components. `EPOCH_LENGTHS = [63, 132, 378]` and `GRAPH_TYPES = ["threshold", "mst", "tmfg"]` are both swept axes, CLI-overridable via `--epoch-lengths`/`--graph-types` — all three graph types are includable, unlike `eigencentrality_sweep_raw.py`'s `mst`/`tmfg`-only grid, because this branch never needs eigenvector centrality's connectivity guarantee. Vectors and regime labels are pulled from `modelling_sweep_raw.py`'s frozen `.joblib` bundle for each `(epoch_length, graph_type)` combo (never refit). Distances are computed on the prepared (L2-normalised) vector, never in PCA space — see [`../math/embedding-geometry.md`](../math/embedding-geometry.md) for the full math, scope rationale, and output schema.

`sweep_run.py` is the orchestrator that sequences all four stages above as separate subprocesses, in dependency order — `modelling_sweep_raw.py`, `eigencentrality_sweep_raw.py`, `spectral_sweep_raw.py`, then `embedding_geometry_sweep.py` last — continuing past a failed step rather than aborting, and printing a pass/fail/elapsed summary at the end. Running `embedding_geometry_sweep.py` before `modelling_sweep_raw.py` has populated the matching `SP500_raw_{63,132,378}d_{threshold,mst,tmfg}.joblib` bundles in `outputs/models/` will fail, since it loads those bundles rather than fitting anything.

`data_visualisation.ipynb` produces one animated gif per `index_code` at the 132d epoch length only (`EPOCH_CONFIGS = [(132, 10)]`) — **4 files** (one per market), saved to the repository root (not under `outputs/` or `images/`); slow to (re)generate. Each gif is a 2×3 grid comparing the raw arm's three graph constructions side by side within a single animation: the top row shows the same raw correlation heatmap three times, once under each of the "Threshold"/"MST-Threshold"/"TMFG-Threshold" column labels, and the bottom row shows the corresponding threshold/MST-threshold/TMFG-threshold network for that window, all three sharing one TMFG-derived node layout (`pos`) so only the edge set changes between panels. This replaced an earlier design that instead overlaid the (since-removed) `raw`/`mg`/`gr` arms one graph-construction-type at a time, at the 378d epoch length only (one gif per `(index_code, graph_type)` combination, 12 files: 4 markets × 3 graph types). It deliberately bypasses `plot_style.py` (`plt.style.use("default")`, a seaborn husl sector palette, a `jet` correlation colormap) rather than using the manuscript style vocabulary every other notebook adopts.

**`build_arm_networks` graph-type wiring**: it builds three filtering methods per window — plain `threshold_graph`, `mst_threshold_graph`, `tmfg_threshold_graph` — stored in the pickled arm dict as `threshold_graphs`/`mst_threshold_graphs`/`tmfg_threshold_graphs`. `modelling_sweep_raw.py`'s `GRAPH_TYPES = ["threshold", "mst", "tmfg"]` resolves the dict key via `"threshold_graphs" if graph_type == "threshold" else f"{graph_type}_threshold_graphs"`. `eigencentrality_sweep_raw.py` uses `GRAPH_TYPES = ["mst", "tmfg"]` only (connectivity requirement, see Stage 3) and resolves the key unconditionally as `f"{graph_type}_threshold_graphs"` via a `GRAPH_KEYS` dict — a bare `graph_type == "threshold"` case would resolve to the wrong, nonexistent key `"threshold_threshold_graphs"` if that restriction were ever lifted without also restoring the conditional. `embedding_geometry_sweep.py` sweeps `GRAPH_TYPES = ["threshold", "mst", "tmfg"]` — including `threshold`, since this branch drops eigencentrality and therefore never needs its connectivity guarantee — and so uses the same **conditional** resolution as `modelling_sweep_raw.py` (`"threshold_graphs" if graph_type == "threshold" else f"{graph_type}_threshold_graphs"`), not the unconditional form the `mst`/`tmfg`-only scripts get away with. `spectral_sweep_raw.py` has no `graph_type` axis at all — it reads `correlation_matrices` directly, never touching any of the three graph dicts.

Every sweep script persists a per-combo `.joblib` bundle (`outputs/models/{tag}.joblib` / `{tag}_eigencentrality.joblib` / `{tag}_spectral.joblib`) containing the fitted scaler/PCA/cluster models plus each clustering method's frozen `kmeans_order`/`hmm_order` and `crisis_id` — enough to relabel new predictions into rank order later without recomputing `fit_regime_order` from scratch. Keep that key-naming consistent in `modelling_sweep_raw.py`'s bundle schema if changed — `embedding_geometry_sweep.py` depends on it, for every `(epoch_length, graph_type)` combo, for its regime-label replay (it is the only one of the three schemas this branch reads at all).

See [`../math/`](../math/) for the algorithms each module implements — this doc covers *how the code is wired together*, not *what the methods compute*. See [`../critical-evaluation.md`](../critical-evaluation.md) for a critical assessment of how much can currently be concluded from results this pipeline has produced historically, and [`../../README.md`](../../README.md) for what's actually on disk in this checkout right now.

## Sweep vs. narrative

**Sweep** (`modelling_sweep_raw.py`, `eigencentrality_sweep_raw.py`, `spectral_sweep_raw.py`, `embedding_geometry_sweep.py`) — runs a grid through embed → cluster → validate (or, for stage 4, embed → distance → MDS), writing one row per combination to a CSV and one figure set per combination to `images/{index_code}_{arm}_{epoch_length}d_{graph_type}/` (or without the `{graph_type}` segment for spectral, which has no such axis). `embedding_geometry_sweep.py` is the one exception to this per-combination folder pattern: since `graph_type` is the axis compared *within* each of its figures rather than the thing a folder is named after, it writes to a single shared `images/{index_code}_{epoch_length}d/` folder regardless of how many `graph_type`s were swept (see [`../math/embedding-geometry.md`](../math/embedding-geometry.md)). This is the artifact for results/comparison tables. Run via `"c:\Users\Abbin\miniconda3\python.exe" modelling_sweep_raw.py` / `eigencentrality_sweep_raw.py` / `spectral_sweep_raw.py` / `embedding_geometry_sweep.py`. **Plotting is the one part of each `run_combo`/`main` that *is* shared** — and for the three regime-detection scripts, shared as one literal implementation, not just a common styling backend: `sweep_common.py`'s `plot_regime_timeline`/`plot_vix_overlay`/`plot_transition_comparison`/`savefig`/`fit_and_rank_regimes` are imported and called identically by `modelling_sweep_raw.py`, `eigencentrality_sweep_raw.py`, and `spectral_sweep_raw.py` — no script keeps its own copy. `embedding_geometry_sweep.py`'s `_plot_selfsimilarity_figure`/`_plot_mds_figure` are a different plot vocabulary (see [`../math/embedding-geometry.md`](../math/embedding-geometry.md)) and stay local to that script. Both layers call into `plot_style.py` for fonts, the regime/neutral colour palette, spine/tick styling, and figure export — see [`../plot_style.md`](../plot_style.md).

**Narrative** (`modelling_walkthrough.ipynb`, `eigencentrality_walkthrough.ipynb`, `spectral_walkthrough.ipynb`) — one notebook per method, one representative configuration, kept as a full step-by-step notebook, covering S&P 500 and Nikkei 225 only (see Stage 3 above). This is where write-up-quality explanation and reasoning lives. `embedding_geometry_sweep.py` has no narrative counterpart — it produces only figures and a results table, with the reasoning that would go in a walkthrough notebook living in [`../math/embedding-geometry.md`](../math/embedding-geometry.md) instead.

**Don't fork a new notebook or script for a parameter change** (a new `epoch_length`, `arm`, or `graph_type` value) — add a grid point to the relevant sweep script instead. Reserve new notebook/script files for genuinely new methodology: a new embedding or clustering method, a new graph-filtering approach, or a new validation/ground-truth check.

A Variational Graph Auto-Encoder (VGAE) embedding method was explored as a candidate 4th descriptor but was shelved and is no longer present anywhere in this working tree — it collapsed to a degenerate, bit-identical embedding across every window on TMFG-threshold graphs (only ever validated on MST-threshold graphs), likely (not confirmed) because TMFG's much higher edge count dilutes window-to-window signal through the GCN's neighbor-sum aggregation. This is why there is no 4th learned-embedding branch alongside Graph2Vec/eigenvector centrality/spectral.
