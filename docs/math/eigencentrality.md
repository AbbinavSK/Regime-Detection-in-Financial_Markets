# Eigenvector centrality: a hyperparameter-free parsimony benchmark

Implemented in `eigencentrality.py`, driven by `eigencentrality_sweep_raw.py`/`eigencentrality_walkthrough.ipynb`. The question this method exists to answer: does Graph2Vec's learned, many-hyperparameter representation (see [`graph2vec.md`](graph2vec.md)) actually earn its complexity, or does the single leading eigenvector of each window's binary adjacency matrix — a deterministic descriptor with no fitting, no random seed, no vocabulary — do just as well at separating Calm/Transitional/Crisis regimes and validating against VIX?

## Binary adjacency, not the distance-weighted graph

`window_centrality(G, stock_names)` builds its adjacency via `nx.to_numpy_array(lcc_subgraph, nodelist=node_order, weight=None)` — explicitly `weight=None`. This matters: every edge in `mst_threshold_graphs`/`tmfg_threshold_graphs` carries a `weight` attribute holding the *Mantegna distance* (`networks.py`'s `mst_graph`/`tmfg_graph`), not the correlation itself, and distance is inversely related to correlation strength (closer = more correlated). Using that weight directly as an adjacency/affinity value would silently invert the graph's meaning. `weight=None` sidesteps it entirely: every present edge counts as 1, regardless of how strong the underlying correlation was. Graph2Vec avoids the same trap independently, via `G.degree(node)` (unweighted by default in `networkx`).

## Largest connected component

`largest_connected_component(G, stock_names)` restricts the eigenvector computation to the graph's LCC, because the leading-eigenvector argument below (Perron–Frobenius) requires an irreducible (connected) non-negative matrix — undefined on a disconnected graph. For `mst`/`tmfg` graphs this is a no-op: both constructions guarantee every stock is reachable (MST by definition; TMFG's triangulation places every node), confirmed empirically (`lcc_frac ≡ 1.0` across all 629 SP500/132d windows checked). The plain `threshold_graph` has no such guarantee and was measured at **43% mean node coverage, ranging 3%–98%, averaging ~158 separate components per window** — this is *why* `eigencentrality_sweep_raw.py`/`eigencentrality_walkthrough.ipynb` restrict `GRAPH_TYPES` to `["mst", "tmfg"]` only. It is not a stylistic choice: without full coverage, `node_order` would vary window to window, and `np.stack(window_stats["v1"].tolist())` would not even be a validly-shaped matrix to run PCA on.

## Leading eigenvector (Perron–Frobenius)

`leading_eigenvector(adjacency)` computes the eigenvector for the adjacency matrix's largest eigenvalue via `scipy.sparse.linalg.eigsh(A, k=1, which="LA")`. For a connected graph, the adjacency matrix is non-negative and irreducible, so Perron–Frobenius guarantees the eigenvalue of largest magnitude is real, simple, and has an eigenvector that can be chosen entirely non-negative — this is eigenvector centrality's classical definition (each node's score is proportional to the sum of its neighbours' scores; the fixed point of that recursive definition is exactly the leading eigenvector).

**Sign handling.** `eigsh`/ARPACK returns an eigenvector defined only up to an overall sign — `v` and `-v` are equally valid solutions. Empirically this flips unpredictably between windows (confirmed directly: one window's ARPACK output was 349 negative entries and one at `~1e-18`, i.e. numerical noise around zero, not a genuine sign conflict). The code corrects this with a single global check, `if v1.sum() < 0: v1 = -v1`, then unit-L2-normalises. There is currently no code path that catches a genuinely broken (non-Perron) eigenvector, so a future revisit should treat that as an open item, not a settled invariant.

**Reproducibility.** `eigsh` is called with no fixed random seed or starting vector (`v0`), which in principle makes it no more reproducible than Graph2Vec's training run to run. Checked directly rather than assumed: called eight times on a real MST-threshold adjacency matrix pulled from the pipeline, all eight results agreed to within $6\times10^{-16}$ — floating-point noise, not genuine variation. This is expected on reflection (Lanczos iteration converges to the true dominant eigenvector regardless of starting point, for a well-separated leading eigenvalue — a convergent numerical method solving a well-posed problem, not a stochastic optimisation like Doc2Vec's SGD), but it's a verified property, not an assumed one. Not because these graphs are trees/bipartite either — checked directly: `mst_threshold_graphs` are an MST backbone plus every above-threshold correlation edge, which routinely creates triangles and breaks bipartiteness.

## Localisation diagnostics

For a unit-L2-normalised `v1`, `window_centrality` reports three descriptors of *how concentrated* the centrality score is across stocks:

- **Participation ratio**: $\text{PR} = 1 / \sum_i v_i^4$. Ranges from 1 (all mass on one node) to $N$ (perfectly uniform). This is the standard localisation diagnostic from the physics of Anderson localisation, repurposed here for network centrality.
- **`max_comp`**: $\max_i v_i$, the single largest centrality entry.
- **Entropy**: $-\sum_i p_i \log p_i$ with $p_i = v_i^2$ (a probability distribution since $\sum v_i^2 = 1$ under L2 normalisation). Computed via `np.log(p, where=p>0, out=log_p)` rather than a naive `p * np.log(p)`, specifically to avoid `0 * -inf = NaN` whenever a `v1` entry underflows to exactly `0.0` — this is the standard `0·log(0) := 0` convention (its limit), not a special case.

**Why this matters for MST specifically**: Martin, Zhang & Newman (2014) show eigenvector centrality localises pathologically on trees — MST's heavy-tailed degree distribution concentrates $v_1$ onto the top hub with exponential decay elsewhere, and the standard remedy (non-backtracking centrality) is degenerate on trees (the Hashimoto matrix is nilpotent on acyclic graphs), so there is no fix, only diagnosis. `eigencentrality_sweep_raw.py` prints a flag (`mean_pr < 10`) as a coarse gate, but this gate is not robust: on a historical grid that also covered the `mg`/`gr` arms, one combo (`SP500/mg/63d/mst`) had `mean_pr = 21.85` (passes the gate) while `median_pr = 4.54` (severely localised in the typical window) — the mean is pulled up by a minority of high-PR outlier windows. See [`../critical-evaluation.md`](../critical-evaluation.md) for the fuller discussion; the takeaway for this doc is that `mean_pr < 10` alone should not be read as "this combo is fine."

## Identity vs. structure: the interpretability trade

`window_centrality` deliberately preserves stock identity — `node_order` follows the canonical `stock_names` ordering, and `argmax_id = node_order[argmax(v1)]` names the single most-central stock in a given window. This is the opposite design choice from Graph2Vec, which anonymises nodes to integers before embedding (`nx.convert_node_labels_to_integers`) precisely so it captures *shape*, not *who*. Eigenvector centrality's `argmax_id` is the concrete interpretability advantage this descriptor offers over Graph2Vec's opaque 128-dimensional vector — at the cost of not being permutation-invariant (a network topologically identical to another but built from a different universe of stocks would look completely different to this descriptor, whereas Graph2Vec would embed them near-identically). On a historical full SP500 grid, `modal_argmax_id` was not stable across even the arm/epoch_length grid (`FIN_BEN` at most configurations, `UTL_LNT` at others) — the interpretability story should be read as "this descriptor can name a plausible answer," not "this descriptor names a single ground-truth systemically-important stock."

## Embedding: exact transform, not approximate inference

`fit_centrality_embed`/`transform_centrality_embed` mirror `graph2vec.md`'s StandardScaler→PCA(0.95) pattern exactly, but with one structural difference worth being explicit about: Graph2Vec's test-time step (`transform_embed`) calls Doc2Vec's `infer_vector`, an *approximate*, iterative re-optimisation against a fixed vocabulary (see `graph2vec.md`'s OOV discussion). `transform_centrality_embed` is a plain, deterministic linear projection — `scaler.transform` then `pca.transform`, no approximation, no fitting step at all. This means the two methods' test-set embeddings are not equally faithful to their respective training fits, which should be kept in mind whenever their held-out performance is compared directly (see [`../critical-evaluation.md`](../critical-evaluation.md)).
