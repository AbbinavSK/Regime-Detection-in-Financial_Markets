# Regime detection: clustering, ranking, and VIX validation

Implemented in `modelling.py`, operating on a PCA-reduced embedding — Graph2Vec's (see [`graph2vec.md`](graph2vec.md)) in `modelling_sweep_raw.py`/`modelling_walkthrough.ipynb`, eigenvector centrality's (see [`eigencentrality.md`](eigencentrality.md)) in `eigencentrality_sweep_raw.py`/`eigencentrality_walkthrough.ipynb`, or the spectral/RMT descriptor's (see [`spectral.md`](spectral.md)) in `spectral_sweep_raw.py`/`spectral_walkthrough.ipynb`. Every function in this file is embedding-agnostic — it operates purely on the `(X, labels, dates)` level — which is exactly what makes all three branches' downstream regime-detection results comparable: the clustering, ranking, and validation logic is identical code, not just similar code, so any difference in their results is attributable to the descriptor, not to divergent pipeline logic. Covers both clustering algorithms the project compares (K-Means, Gaussian HMM), how their arbitrary cluster labels are turned into comparable Calm/Transitional/Crisis regimes, and how the resulting crisis signal is scored against a validation series (VIX, currently the only one wired up).

## K-Means

`cluster_kmeans(X, k=3)` runs standard Lloyd's-algorithm K-Means: minimize within-cluster sum of squared distances to $k$ centroids. `n_init=20` runs 20 random centroid initializations and keeps the lowest-inertia result, since K-Means' objective is non-convex and sensitive to initialization. `k` is fixed at 3 throughout the project (Calm/Transitional/Crisis). The K-Means elbow (inertia across a range of $k$) that originally justified $k=3$ is a one-off diagnostic, not part of the reusable pipeline — it's inlined directly in `modelling_walkthrough.ipynb`'s S&P 500 section only (`k = 2..9`), rather than a function in `modelling.py`.

Each rolling window is clustered independently — K-Means has no notion of time or sequence.

## Gaussian HMM

`cluster_hmm(X, k=3, n_seeds=20)` models the regime sequence as a Hidden Markov Model: $k$ hidden states (regimes), each emitting the observed PCA embedding at every rolling window from a per-state multivariate Gaussian. `covariance_type="diag"` assumes independent variance per PCA dimension within each state (a diagonal, not full, covariance matrix) — keeping the parameter count linear rather than quadratic in embedding dimensionality. Unlike K-Means, the HMM has explicit **temporal structure**: a $k\times k$ transition matrix governing how likely the market is to stay in or switch out of a regime from one window to the next.

Fitting uses Baum-Welch (EM for HMMs, `n_iter=200, tol=1e-4`), which only finds a local optimum — different random initializations can converge to meaningfully different results, so **HMM fitting is not seed-stable** the way K-Means effectively is with `n_init=20`. `cluster_hmm` compensates by trying `n_seeds` (default 20) different `random_state` values and keeping whichever model has the highest training log-likelihood (`model.score(X)`).

The HMM's analogue of the K-Means elbow is an AIC scan: fit (best-of-10-seeds) models across a range of state counts (`n = 2..9`) and compare each one's AIC ($2\times\text{params} - 2\times\text{log-likelihood}$, penalizing complexity so the scan doesn't just favor the largest state count). Like the K-Means elbow, this was used once to justify $k=3$ and is inlined directly in `modelling_walkthrough.ipynb`'s S&P 500 section only, not a function in `modelling.py`. No BIC and no silhouette score are computed anywhere in the codebase.

## Ranking clusters into regimes

Raw cluster labels (from either algorithm) are arbitrary integers with no inherent Calm/Transitional/Crisis meaning — cluster `0` might be "Crisis" in one run and "Calm" in the next (the standard label-switching problem for clustering/mixture models), which would make results incomparable across the sweep's `index_code x arm x epoch_length x graph_type` grid.

`fit_regime_order(labels, mu, k)` fixes this using $\mu$ — the mean off-diagonal correlation of the window's network (see `networks.mu_offdiag`), the project's crisis indicator (correlations spike when the whole market moves together). Called on **train labels/μ only** (never re-derived from test), it computes each cluster's mean $\mu$, sorts clusters by it, and defines the **highest-$\mu$ cluster as "Crisis"** regardless of its raw label — returning `(order, rank_of_cluster, crisis_id, cluster_mean_mu)`, where `order` is the frozen train-derived permutation and `crisis_id` is fixed for everything downstream. `apply_regime_order(labels, order)` then does the pure relabelling (`rank_of_cluster[labels]`) for both train and test label sequences through that *same* frozen `order` — it recomputes nothing from the labels it's given, which is what keeps a test sequence's regime identity comparable to train's rather than re-litigated from test's own cluster geometry.

`hmm_transitions(model, order)` reorders the HMM's transition matrix rows/columns by that same $\mu$-based order, so $P_{ij}$ always lines up with Calm/Transitional/Crisis consistently. The diagonal $P_{ii}$ is the self-transition probability (staying in regime $i$ for one more window). Treating consecutive same-regime windows as a geometric distribution with success probability $P_{ii}$, the expected dwell time is:

$$\text{dwell}_i = \frac{1}{1 - P_{ii}}$$

## Validation against VIX (or any other series)

`validate_regime(labels, dates, series, threshold, crisis_id)` scores a labelled sequence's predicted-crisis membership against a validation series, using the market convention that VIX > 30 marks an elevated-volatility/crisis period — but the function itself is generic (any `series`/`threshold`). It takes `crisis_id` directly rather than re-deriving it: nothing in this function recomputes a mu-ranking, it only ever consumes the frozen `crisis_id` that `fit_regime_order` produced on train.

Only a **point-in-time** ground truth is computed: the validation series' value on the window's exact end-date, aligned via `reindex` + `sort_index` + forward-fill (`series.reindex(series.index.union(dates)).sort_index().ffill().reindex(dates)`) so a window's end-date always has a value even if the series itself doesn't trade on that exact date. There is currently no window-max validation (checking whether the series spiked *anywhere* over the preceding window rather than just at its end-date) anywhere in the codebase — `validate_regime`'s signature has no `epoch_length`/`mu` parameters to support it.

The predicted signal `pred` is binary: 1 wherever a window's cluster label equals `crisis_id`, 0 otherwise — derived purely from the correlation-network clustering, with the validation series used only afterward for scoring, never as a clustering input. `binary_f1(pred, actual)` computes standard precision/recall/F1 from the resulting confusion counts (each guarded against division-by-zero, returning 0.0 rather than raising):

$$\text{precision} = \frac{TP}{TP+FP} \qquad \text{recall} = \frac{TP}{TP+FN} \qquad F_1 = \frac{2 \cdot \text{precision} \cdot \text{recall}}{\text{precision} + \text{recall}}$$

`validate_regime` returns a dict (`series_eod`, `pred`, `crisis_point`, `point`) where `point` is the `(precision, recall, f1)` triple; called separately on train and test labels/dates in `modelling_sweep_raw.py`/`eigencentrality_sweep_raw.py`/`spectral_sweep_raw.py`, but only for `index_code == "SP500"` — the other three markets (Nikkei 225, FTSE 350, CSI 300) have no validation series downloaded, so they get no F1/precision/recall at all, only the structural `empirical_transitions` comparison. With test sets as small as a few dozen windows and true "VIX > 30" events rarer still, F1 here is sensitive to a handful of misclassified windows — see [`../critical-evaluation.md`](../critical-evaluation.md) for a worked example of exactly how much a small number of boundary windows can move it.
